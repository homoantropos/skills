# 🔴 KILLED — must not ship

- False premise that leads to wrong results or crashes (age as year difference, money in float, "this field always exists", one time zone, unlimited storage). Fixing a line doesn't help; it repeats. Minor consequence → rank by consequence.
- Tests pass, results guaranteed wrong. Silent lies outrank crashes.
- Guaranteed crash: unhandled errors.
- Freeze or blocked scrolling.
- Storage overflow, writes fail.
- Security hole: secret in code, config or history; injection (SQL, shell, HTML, path); missing or bypassable auth or access check; personal data exposed in logs, URLs or responses.
- Irreversible data loss: destructive migration without rollback, delete or overwrite without backup.
- Two partial updates of one server record sent in parallel to an endpoint that read-modify-writes the whole record → the later write silently drops the earlier one's change, and both answer 200. Beats the 🟠 "async races" case: it happens on every normal save, and nothing reports the loss.
- After an await or in a late callback, code acts on shared state by key or by a "current" field without checking it is still the object it started with (a queue entry, the current connection, the next step's position) → a newer edit takes the old attempt's failure and is deleted, a stale close kills the new connection, a step is sent before the dependency inserted ahead of it. Beats the 🟠 "async races" case: it fires on every reconnect or edit made during a send, not in a narrow window, and can delete user data.
- A busy/open flag reset only on the happy path (success events, a non-empty result, after an early-return guard) → a dropped connection, an error frame, an empty result or a missing host leaves it set: input locked or feature dead until restart. Beats the 🟡 "missing error handling" case: the user is stuck, same as a freeze.
- A retry of a non-idempotent request that mints a new idempotency key (fresh key per manual retry after a client timeout, or a missing "retryable" flag defaulted to the drop-key branch) → the first request still reached the server, so the action runs twice. Beats the 🟠 "mid-operation edge cases" case: an external action can't be undone, and slow networks make it routine.
- A queued request whose result is unknown (timeout, dropped connection) never counts against its retry limit → it is resent forever, blocks everything behind it with no error shown, and duplicates if the server ignores the idempotency key. The queue is frozen for good.
- Two consumers process the same queue at once (a single-flight guard released when a timeout wins instead of when the work ends, or a handler subscribed once per component instance) → each item is sent twice: duplicates created, position-addressed deletes remove rows nobody touched. Beats the 🟠 "async races" case: a slow pass or an open screen is enough.
- Sent items removed by position (`shift()`) while another writer replaces or re-keys the stored array → the sent item stays in storage and is sent again next pass. Beats the 🟠 "async races" case: it happens under normal timing.
- A storage API that reports failure by returning false is awaited as if it throws → the caller deletes the source after a write that failed. Beats nothing lower: the caller did check, the API hid the failure, and the data is gone for good.
- A resend helper that swallows errors and returns normally → the replay treats a failed send as delivered and drops the stored action. The user's offline work is lost silently.
- An early return or gate that tests a proxy instead of the real condition (an unrelated queue is empty, only one of two valid options is checked) → the work is skipped every time on that path; for stored offline actions, they are never sent. Guaranteed for that path and invisible to tests that use the other one.
- A paid or external side effect chained on every emission of a stream assumed to emit once (progress events, a timer-based retry) with no take-first after the final-response filter → the effect repeats every tick and the finalizer that clears the spinner never runs. Unbounded real cost.
- A list merge that inserts and reorders server items but never removes any → items deleted elsewhere stay on screen, in the local snapshot and in totals, across restarts. Guaranteed wrong data that persists.
- A reusable component that hardcodes an option's initial value instead of reading the caller's flag → hidden while every caller passes the same value; the first one that differs triggers an outbound action the user never asked for. Can't be undone.
- An ambient "current record" context set by a page for a global action and not cleared on leave, or re-set by a late response after the page is destroyed → the global action writes into a record the user already left. Wrong data in the wrong place, silently.
- LLM tool-call arguments used raw → models send 0 or empty for unspecified optional numbers and human labels where ids or enum codes are expected: zero overrides a real price, a filter matches nothing, or every call fails validation. Guaranteed whenever the user names no value; wrong money is a wrong result.
